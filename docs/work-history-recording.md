## 왜 트리거인가

업무를 고치는 경로가 **두 개**다 — 상태 배치 변경 RPC(`work_update_statuses`, 드래그·KPI 존 이동)와
수정 폼(`updateWork` → works 테이블 직접 UPDATE). RPC 안에만 INSERT 를 넣으면 수정 폼 경로가 조용히
새서 "이력이 가끔 비는" 신뢰 문제가 된다. 트리거는 두 경로를 한 곳에서 잡고 앱 코드를 안 건드린다.

트리거 관습은 이미 이 DB 에 있었다 — `calendar_log_delete`(plpgsql · SECURITY DEFINER ·
search_path 고정 · `current_setting` 탈출구). 같은 모양으로 맞췄다.

**대가 1건**: 문단↔목록 전환·목록 단계 변경은 이제 **아무 데도 안 남는다**. 에디터가 목록 마커를

**② 본문 비교를 정규화한 잣대로 바꿨다.** 원문 대신 아래를 비교한다(prev/next 에는 원문을 그대로 남긴다).

**한 번 틀렸다가 되돌린 설계**: 처음엔 공백을 *전부* 지우고 비교했다. 지시의 앞부분은 지켰지만

## 검토에서 잡은 내 설계 오류 2가지

적대 검토(27개 에이전트) 결과 confirmed 6건 — 뿌리는 둘이었다.

**① 본문 비교 기준이 틀렸다.** 처음엔 `coalesce(nullif(content_fmt,''), task)` 로 "화면에 보이는
본문"을 비교했는데, 실제로는
- `task` = `제목줄\n본문` 평문이고 두 경로 모두 **항상** 갱신한다
- `content_fmt` = ProseMirror 직렬화 JSON(`{"version":1,"doc":{...}}`)이고 **제목이 빠져 있다**

그래서 ⓐ 서식이 붙은 업무(19건)의 **제목만** 고치면 content_fmt 가 그대로라 이력이 0줄이 되고,
ⓑ 평문→서식 첫 저장에서 prev 는 평문·next 는 JSON 덩어리가 그대로 박혀 사람이 못 읽는 이력이 된다.
→ **본문 비교는 `task` 로**, 서식 변경은 값을 남기지 않고 `서식 / '본문 서식 변경'` 표시만.

**② "완료일은 상태 전이에 딸려온다"는 전제가 거짓이었다.** `src/api/works.ts` 의
`applyStatusRules` 는 `end_date: status === '완료' ? (end || 오늘) : ''` 이고, 그 아래 보호 장치는
**완료가 아닐 때만** 걸린다(`if (p.status !== '완료' && p.end === undefined) delete patch.end_date`).
수정 폼·인라인 편집 모두 `end` 를 안 보낸다. 즉 **이미 완료된 업무를 아무 이유로나 저장하면
완료일이 오늘로 덮인다.** 상태는 안 바뀌므로 이력에도 안 남을 뻔했다.
→ **완료일도 기록**하되, 상태가 함께 바뀐 경우는 중복이라 제외.

## 곁다리로 고친 앱 버그 — 완료일 덮어쓰기 (같은 날, 사용자 지시)

**증상**: 이미 완료된 업무를 아무 이유로나 저장하면(장소 한 글자만 고쳐도) 완료일이 오늘로 덮여
과거 완료일이 사라졌다. 수정 폼도 인라인 편집도 `end` 를 안 보내므로 **항상** 걸렸다.

**고친 방법** — `updateWork` 에 `prevStatus`(고치기 전 상태)를 받아 **완료로 새로 넘어오는 순간에만**
자동으로 채운다:

```ts
const becameDone = p.status === '완료' && p.prevStatus !== '완료'
if (p.end === undefined && !becameDone) delete patch.end_date
```

가드를 단순히 푸는 것(`if (p.end === undefined) delete patch.end_date`)만으로는 안 된다 —
그러면 **진행중→완료 전환에서 완료일이 안 채워지는** 반대 문제가 생긴다(WorkWrite 경유 전환도
`end` 를 안 보낸다). 그래서 전환인지 아닌지를 알아야 했다. `prevStatus` 미전달 시에는 종전 동작이라
다른 호출부는 영향받지 않는다. 호출부 2곳에 넘겼다 — `Work/index.tsx` confirmEdit(인라인, 상태
불변이라 `item.status`), `WorkWrite.tsx`(수정 모달, `editing.status`).

**검증** — 실제 앱 코드 경로(dev 서버의 `updateWork`)를 그대로 호출하고, 위 이력 기록으로 교차확인:

|---|---|---|
| 완료 업무(#150, 완료일 08-10) 값 변경 없이 재저장 | 완료일 유지 · 이력 0줄 | 08-10 유지 · 0줄 (updated_at 은 갱신 → UPDATE 가 실제로 돌았음) |
| 진행중 업무(#123) → 완료 전환 | 완료일 오늘 자동 · 상태 1줄 | 08-12 채움 · `상태 진행중 → 완료 · 조성범` |

두 번째 줄은 **이력 기록이 앱 실경로에서 작성자까지 제대로 잡는다**는 증거이기도 하다.
검증에 쓴 업무는 원래 값으로 되돌렸고 검증으로 생긴 이력 행도 지웠다(work_history 0행).
