## 왜 트리거인가

업무를 고치는 경로가 **두 개**다 — 상태 배치 변경 RPC(`work_update_statuses`, 드래그·KPI 존 이동)와
수정 폼(`updateWork` → works 테이블 직접 UPDATE). RPC 안에만 INSERT 를 넣으면 수정 폼 경로가 조용히
새서 "이력이 가끔 비는" 신뢰 문제가 된다. 트리거는 두 경로를 한 곳에서 잡고 앱 코드를 안 건드린다.

트리거 관습은 이미 이 DB 에 있었다 — `calendar_log_delete`(plpgsql · SECURITY DEFINER ·
search_path 고정 · `current_setting` 탈출구). 같은 모양으로 맞췄다.

## 기록하는 것 / 안 하는 것

| 기록 | 안 함 |
|---|---|
| 상태 · 담당자 · 예정일 · Remind · 내용 · 서식 · 완료일(상태가 안 바뀐 경우만) | 순서 · 첨부 · 구분 · 부서 · 장소 · 휴지통 왕복 |

- **Remind 를 넣은 이유**: 완료 카드를 Remind 존으로 옮기면 status 는 '완료' 그대로이고 remind 만
  바뀐다. 상태만 기록하면 분명히 카드를 옮겼는데 이력이 한 줄도 안 남는다.
- **휴지통 왕복 제외**: 넣었다 뺐다 하는 것이 가짜 이력을 만들면 안 된다.

## 검토에서 잡은 내 설계 오류 2가지

적대 검토(27개 에이전트) 결과 confirmed 6건 — 뿌리는 둘이었다.

**① 본문 비교 기준이 틀렸다.** 처음엔 `coalesce(nullif(content_fmt,''), task)` 로 "화면에 보이는
본문"을 비교했는데, 실제로는
- `task` = `제목줄\n본문` 평문이고 두 경로 모두 **항상** 갱신한다
- `content_fmt` = ProseMirror 직렬화 JSON(`{"version":1,"doc":{...}}`)이고 **제목이 빠져 있다**

그래서 ⓐ 서식이 붙은 업무(19건)의 **제목만** 고치면 content_fmt 가 그대로라 이력이 0줄이 되고,
ⓑ 평문→서식 첫 저장에서 prev 는 평문·next 는 JSON 덩어리가 그대로 박혀 사람이 못 읽는 이력이 된다.
→ **본문 비교는 `task` 로**, 서식 변경은 값을 남기지 않고 `서식 / '본문 서식 변경'` 표시만.

**② "완료일은 상태 전이에 딸려온다"는 전제가 거짓이었다.** `src/api/works.ts` 의
`applyStatusRules` 는 `end_date: status === '완료' ? (end || 오늘) : ''` 이고, 그 아래 보호 장치는
**완료가 아닐 때만** 걸린다(`if (p.status !== '완료' && p.end === undefined) delete patch.end_date`).
수정 폼·인라인 편집 모두 `end` 를 안 보낸다. 즉 **이미 완료된 업무를 아무 이유로나 저장하면
완료일이 오늘로 덮인다.** 상태는 안 바뀌므로 이력에도 안 남을 뻔했다.
→ **완료일도 기록**하되, 상태가 함께 바뀐 경우는 중복이라 제외.

## 검증 (전부 되돌리는 트랜잭션 안에서 — 실데이터 무변경)

| 조작 | 기대 | 결과 |
|---|---|---|
| 상태 진행중→완료 | 1줄 | 상태 `진행중 → 완료` |
| 담당자만 변경 | 1줄 | 담당자 `박세리 → 박주봉` |
| 본문만 변경 | 1줄, 사람이 읽는 글 | 내용, 평문 그대로 |
| 서식만 변경 | 1줄, JSON 없이 | 서식 `→ 본문 서식 변경` |
| Remind 토글 | 1줄 | Remind `꺼짐 → 켜짐` |
| 완료 업무 재저장(완료일만 오늘로) | 1줄 | 완료일 `2025-06-19 → 2026-08-12` |
| 순서(sort_order)·장소만 변경 | 0줄 | 0줄 |
| 휴지통 넣기 / 휴지통 안에서 수정 | 0줄 | 0줄 |
| 값이 같은 재저장(no-op) | 0줄 | 0줄 |
| 탈출구(`app.work_skip_history=1`) 켠 변경 | 0줄 | 0줄 |

- **작성자 귀속**: `set local request.jwt.claims` 로 로그인 사용자를 흉내 내 검증 → `author = 조성범`.
  스크립트·서비스롤 경로는 `시스템`으로 남는다.
- **권한**: 게스트(anon)로 조회 시 0행. 팀원 이상만 읽힌다. 쓰기 정책은 **일부러 두지 않았다** —
  넣고 고치는 것은 트리거만 할 수 있다.
- **RPC 노출**: advisors 0028/0029 에 `work_log_changes` 가 잡히지만(기존 `calendar_log_delete` 와 동일),
  직접 호출해도 이력이 만들어지지 않음을 확인했다.
- 롤백 후 `work_history` 0행 · 대상 업무 원래 값 그대로임을 매번 재확인.

## 되돌리는 법

```sql
drop trigger if exists works_log_changes on public.works;   -- 기록만 멈춤(표는 유지)
drop function if exists public.work_log_changes();
drop table if exists public.work_history;                    -- 쌓인 이력까지 버릴 때만
```
트리거를 먼저 떼야 한다. 표를 먼저 지우면 업무 수정이 전부 실패한다.

## 남은 것 (사용자 지시 대기)

**`src/api/works.ts` 의 완료일 덮어쓰기는 앱 버그로 남아 있다.** 이력이 그 사실을 기록해 주기는
하지만 덮어쓰기 자체를 막지는 않는다. 고치려면 한 줄:

```ts
// 완료일은 '완료로 새로 전환될 때'만 자동으로 채운다 — 이미 완료인 행을 재저장할 때 오늘로 덮지 않게
if (p.end === undefined) delete patch.end_date
```
(완료 전환 시 자동 오늘 규칙은 RPC `work_update_statuses` 와 `createWork` 가 이미 갖고 있다.
다만 WorkWrite 경유 완료 전환도 `end` 를 안 보내므로, 고치기 전에 그 경로를 함께 확인할 것.)
